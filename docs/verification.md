## 3. hooks 連携の統合テスト手順（実プロジェクトでの発火確認）

### 3.1 登録と settings.json マージの確認（V-02）

1. 事前状態を 3 パターン用意する: (a) `.claude/` なし、(b) `settings.json` に既存 hooks（ダミーの Stop hook）あり、(c) `settings.json` が不正 JSON。
2. 各パターンのフォルダを terminal-app へ D&D 登録する。
3. 確認: (a)(b) では `settings.json` に `terminal-app` マーカー付きの Stop / Notification エントリが追加され、(b) の既存ダミー hook が原文のまま残る。バックアップ `settings.json.terminal-app.bak` が作られる。(c) ではファイルが**一切変更されず**、UI にエラーが表示され登録もされない。
4. 同じフォルダを再登録（または登録済みのまま再度マージ）しても、エントリが重複しないこと（冪等性）。

### 3.2 Stop 発火 → 「完了」（V-04）

1. サンドボックスを登録済みにし、terminal-app を起動しておく。
2. `cd C:\dev\sandbox-hook-test` で `claude` を起動し、短いプロンプト（例: 「1+1 を計算して」）を送る。
3. 応答完了（Stop 発火）で該当タイルが「完了」（緑 ✓）へ変わり、相対時刻が「たった今」になることを目視確認する。
4. **1 秒以内（NFR-01）の判定はログ差分で行う**（2026-07-11 変更: ストップウォッチ目視 → 受信時刻と UI 描画時刻のログ差分計測）:
   アプリログ `%APPDATA%\terminal-app\logs\app.log` で、当該イベントの `event 受信:`（受信時刻）に対応する
   `ui-latency: 受信→描画完了 <N>ms` 行（renderer が描画完了を main へ通知した時点との差分）を確認し、
   **N ≤ 1000** であること。目視のストップウォッチ計測は行わない。

### 3.3 Notification 発火 → 「確認待ち」（V-05）

1. 同じセッションで、許可が必要な操作を指示する（例: 許可未設定のコマンド実行を依頼し、許可ダイアログで止める）。
2. Notification 発火時点で該当タイルが「確認待ち」（アンバー ?）になる。
3. 補助確認: 60 秒放置の入力待ち通知でも「確認待ち」になること（Notification の別種別、design.md 4.3）。

### 3.4 擬似イベント注入（アプリ単体の統合テスト。V-13, V-15, V-16）

実セッションを 16 個並べるのは高コストのため、受信サーバへ curl で直接 POST して代替する。

```
curl.exe -s -X POST http://127.0.0.1:41321/terminal-app/event ^
  -H "Content-Type: application/json" ^
  -d "{\"hook_event_name\":\"Stop\",\"session_id\":\"s-test-01\",\"cwd\":\"C:\\\\dev\\\\sandbox-hook-test\"}"
```

- `session_id` / `cwd` / `hook_event_name` を変えながら投入し、V-13: ステータスバー件数が状態別に正しく増減すること、V-15: 16 プロジェクト×各状態でタイルグリッドが破綻しないこと、V-16: エラー相当イベントで静的な赤になることを確認する。
- エラー相当イベントの形式は design.md 4.8 の定義に従う（2026-07-11 確定。例:
  `{"hook_event_name":"SessionEnd","session_id":"s-err-01","cwd":"C:\\dev\\sandbox-hook-test","reason":"other"}`）。
- 不正 JSON・未知プロジェクトの cwd を投げ、タイルが変化せずログにのみ記録されること（design.md 10 章）。
- 日本語を含むパスを注入する場合はコマンドライン引数に JSON を直接書かず、実 hook と同じく **stdin 経由**
  （`--data-binary @-` またはファイル `@payload.json`）で送る（Windows の ANSI 変換で文字化けするため）。

### 3.5 登録解除で除去（V-03）

1. 3.1 (b) のプロジェクトを設定画面から登録解除する。
2. 確認: `terminal-app` マーカー付きエントリのみが消え、既存ダミー hook と他の設定キーが登録前と完全一致（diff で比較）。空になった配列・`hooks` キーが残骸として残らない。

### 3.6 アプリ未起動時の無害性（V-14）

1. terminal-app を終了した状態で、登録済みサンドボックスの `claude` セッションを実行・完了させる。
2. 確認: セッションがエラー表示や追加のユーザー操作なしで完走する（curl の失敗が exit 2 にならず無害であること。design.md 4.6）。応答完了までの体感遅延が hook タイムアウト（2 秒）を超えないこと。

### 3.7 受信サーバのバインド確認（V-19）

`netstat -ano | findstr 41321` で LISTEN が `127.0.0.1:41321` のみであること（`0.0.0.0` で開いていないこと）を確認する。

### 3.8 アイドル負荷（V-20）

全タイル「実行中」以外（アニメーションが発光のみ）の状態で 5 分放置し、タスクマネージャーで CPU がほぼ 0%（目安 1% 未満）であることを確認する。

## 5. 自動テストの方針（単体・統合・E2E の分担）

| 層 | 対象 | ツール案（OPEN-01 未確定のため両案併記） | 優先度 |
|----|------|------------------------------------------|--------|
| 単体 | **settings.json マージ/除去**（最重要。既存 hooks あり/なし/不正 JSON/重複登録の境界値）、状態遷移ロジック（4 章の表をそのままテストケース化）、cwd→プロジェクト対応付け（大文字小文字・サブディレクトリ・不一致） | Electron 案: Vitest ／ Tauri 案: `cargo test`（＋フロント側 Vitest） | 高（実装と同時に整備） |
| 統合 | ローカル HTTP 受信 → 状態ストア反映 → ステータスバー件数。不正入力の破棄 | 同上（受信サーバをテストプロセス内で起動し curl/fetch で叩く） | 高 |
| E2E | 起動 → D&D 登録 → 擬似イベント → タイル表示 → 設定変更の一連 | Electron 案: Playwright（Electron ドライバ）／ Tauri 案: WebDriver（tauri-driver）＋Playwright | 中（主要フロー 1 本から） |
| 手動枠 | ウィンドウ前面化（V-09, V-10）・発光の見え方（V-06）・実 hooks 発火（3.2, 3.3） | 自動化困難（OS フォーカス・実セッション依存）なため手動 E2E チェックリストで担保 | — |

CI は設けず（本人のみ・ローカル前提）、実装時に「コミット前に単体＋統合を実行」を運用ルールとする。

## 7. MVP 完了判定の手順

1. 自動テスト（5 章の単体＋統合）が全件パスしていること。
2. 6 章の手動 E2E チェックリストを通しで実施し、**must 対応の項目（#1〜#12, #14〜#16）がすべて ○** であること。#13（should）は判定対象外として結果のみ記録する。
3. 2 章の対応表で must の AC（AC-01〜AC-16）すべてに ○ が付くこと。×・保留が 1 件でもあれば MVP 未完了。
4. 9 章の未確定検証タスクのうち、OPEN-04（実行中検知）の採否が決まっていること（案 B 採用でも可。T-9 の扱いを記録）。OPEN-03 は「検知できた範囲」を記録すれば MVP 完了を妨げない（spec.md AC-16 の但し書きどおり）。
5. 実施結果は `docs/verification-log.md`（実施日・実施者・各項目の○×・証跡）として記録する（初回実施時に作成）。

## 8. 検証しないこと（対象外の明示）

- OS トースト・サウンドの鳴動仕様（OPEN-02。次期スコープで検証計画を追加する）
- 完了履歴・タイムライン（REQ-14: could）
- 多人数・ネットワーク越しの利用、Windows 11 以外の OS
